# vocos int8 —— ❌ 不可用（相位全毁）

> 结论：**这条路在本工具链上不成立。** 硬件段最快（9.50 ms），但波形相关只有 **0.186**，听感是噪声。

## 1. 读数

| | int8 | fp16（对照） |
|---|---:|---:|
| 模型体积 | **18.7 MB** | 31.3 MB |
| 硬件段 | **9.50 ms** | 19.29 ms |
| `mag` 相关 | 0.102（早期误测，见 §4） | 0.99868 |
| `cos` 相关 | 0.106 | 0.73168 |
| `sin` 相关 | 0.11 | 0.72839 |
| **波形相关** | **0.186** ❌ | **0.969–0.978** ✅ |
| 相位平均误差 | **81.1°** | 22.5° |

## 2. ★ 根因（A 级，不是猜的）

**诸葛的 `CosNode` / `SinNode` 没有实现量化参数**，运行期打印：

```text
ZhugeQuantParams Not Implemented! Using Default Imeplementation!
```

后果链条（**注意第 2 条，这才是致命的那条**）：

1. **角度张量的 scale 被写成常数** `0.49766457`，而模型声明的是 `0.45043343`
   ⇒ **偏差 10.4%**；量化步长因此固定为 **0.4975 rad**，板上角度输出只剩
   **256 个离散值**（±63.69、步长 0.4975，与常数逐位吻合）。
2. **更严重：`Cos` 的输出与输入角度脱钩。** 把板端 cos 输出拿去拟合"真实角度 → 圆周 256 步"，
   命中率只有 **0.4%–4.9%**（≈1/256 的随机水平）；同一个 int8 code 分箱内板端 x 有 **36 个不同值**，
   同一个 x 值又出现在 `-128…-121` 各个 code 上 ⇒ **板端的 `Cos` 根本不是角度的函数**。
3. 所以相位全毁。

> ⚠️ **别把结论说成"角度被量化得太粗"**。实测否证了那个说法：
> 按板端规格（`round(a/0.45043343)` 后 clip ±127）在**真实角度**上模拟 int8，
> `cos/sin` 仍有 **0.9645 / 0.9711**；先折到 [-π,π] 再量化或允许环绕，更是 0.9916。
>
> **准确说法：`Cos` 算错了，不是角度不够细。**

## 3. 试过且失败的三条补救路线（不必再试）

### 3.1 `--mix_precision`

| 做法 | 结果 |
|---|---|
| `auto` | 0.885 → **0.898**（cos/sin **没动**） |
| 自定义 CSV（132 行，把 Cos/Sin 标成 fp16） | **0.12171**（更差） |
| 5 个算子（角度路径）标 fp16 | 0.12381（更差） |
| 全 fp32 | 板上失败：`Op is NOT bound to any backend, op_id = 137, type_key = icraft::xir::TransposeNode` |

CSV 格式（`op_type` 不是 `type`）：
`op_id,op_type,dtype,value_range_in_bits,saturation,per,order`

### 3.2 把三角函数搬出图外

把角度作为**第 4 个 fp32 输出**，cos/sin 在 C++ 里算：

| 阶段 | 结果 |
|---|---|
| 五段编译 | 全部 `rc=0` |
| 板上运行 | `rc=0` |
| **角度仍是 256 级**（±63.7） | ⇒ **问题不在三角在哪算，在角度张量本身已被量化成常数 scale** |
| `cos` 相关 | **0.1060** |

**⇒ 这条路彻底不成立。**

### 3.3 模拟验证"是不是角度饱和/回绕导致的"

有人猜是角度超出 int8 范围（−149.84…+142.16 rad）导致回绕。**实测否定**：
在真实角度上模拟 int8 量化（只有 2.41% 饱和），算出的 `cos/sin` 相关仍有 **0.9645 / 0.9711**。

⇒ **不是饱和问题，是 scale 常数写错。**

## 4. ⚠️ 早期读数 0.102 是个假数（教训）

第一次测 `mag` 得到 0.102，以为 int8 把幅度也毁了。真相是**两边喂的 mel 不是同一份**：
一边 `48000 = 600×80`，另一边 `36400 = 80×455`。修正后 `mag = 0.885`。

**教训：比对前必须 md5 两边 + 断言 `npu_in[0,0,:T,:] == mel.T`。**

## 5. 结论

- **int8 省下的 9.79 ms（19.29→9.50）换不来可用音频**，不值得救。
- 唯一可行解是**整模型 fp16**：不用校准集，代价体积翻倍、硬件段 2.02×。
- 若日后厂商修好了 `Cos/Sin` 的量化参数，int8 可能重新可用——**届时先量角度张量的离散级数**，
  256 级就是坏的，别只看波形相关。

## 6. 校准集（int8 必需，留着备用）

`qtset/` 里是 `mel_*.bin`，每个 **48000 B = 600×80**，直接复用即可。
