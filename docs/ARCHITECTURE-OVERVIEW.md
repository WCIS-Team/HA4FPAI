# 整体逻辑与「实现了哪些 HA 逻辑」

> 2026-10-31 现状盘点。**先说清一件事：klar engine 不是 HA 的替代品，
> 它是 HA 的「对话代理插件」。我们没有 HA，所以自己补了 HA 负责的那几层。**

## 一、当前完整链路

```
 ┌─ 输入侧（板上无麦克风，等硬件）─────────────────────────────┐

 │    ↓ decimate3-mavg3（实测 -12.3dB @20kHz 抗混叠）          │

            ↓

 │                                                              │
 │  10300 KWS ─ 唤醒词「小克」                                  │
 │        │  命中 → 触发下一环                                  │
 │        ↓                                                     │

            ↓  文本
```

## 二、我实际实现了哪些「HA 的逻辑」

HA 在这条链路里负责 4 件事。逐条对照我做到什么程度：

| # | HA 的原职责 | 我的实现 | 状态 | 证据 |
|---|---|---|---|---|
| 1 | **实体表**（房间/设备/命名的唯一真值） | `make_registry.py` 生成 `core.entity_registry` + `core.area_registry`（两层 JSON 格式是踩出来的） | ✅ 完成 | 日志 `6 Entitäten, 3 Räume, 0 Etagen ... geladen` |
| 2 | **意图执行器**（把 intent 落到设备） | `klar_executor.py` 双通道：通道A 消费 klar 的 `{intent,slots}`，通道B 直连命令表 | ✅ 完成（这是 HA 最核心、最容易漏的一层） | 8/8 命令实测通过 |
| 3 | **设备接入**（Zigbee/WiFi/Modbus…） | 不需要——被控设备就是这块板自己的 HTTP API（8091/8092/8093） | ✅ 用板内 HTTP 替代 | 全部端点实测 |
| 4 | **状态查询**（"灯开着吗"） | `act_status()` 并发读三个服务；`door_status` 查门禁 | ✅ 部分 | 实测返回「录制 off；画面 无有效帧」 |

**外加我补了 HA 没有、但这条链必须有的东西：**
- **语音 I/O 层**（HA 靠 Wyoming 集成，没有板上实现）→ `voice_gateway.py`
- **重采样**（HA 不管采样率）→ linear / decimate3-mavg3，都做过 A/B
- **多因子开门**（HA 的 lock 域只是一条命令）→ 口令+人脸+防伪+声纹四道闸
- **声纹**（HA 没有）→ `voiceprint.py`（campplus-zh，同人 cos 1.000 / 异人 −0.07）

## 三、HA 有、但我**故意没做**的逻辑（及为什么）

| HA 的能力 | 为什么没做 | 影响 |
|---|---|---|
| **多轮上下文** | klar engine 自带 `conversation_id`，但 executor 每次新建会话，没接上 | 「再关掉」这类指代会失效 |
| **自动化/场景**（`automation.yaml`） | 板上没有定时触发器、没有条件判断引擎 | 「每天7点叫我」做不到 |
| **定时器真正执行** | klar 只会输出 `HassStartTimer`，到期动作没人做 | 「十分钟后提醒我」只播报"已开始"，不会真提醒 |
| **实体状态历史**（recorder） | 板子没数据库；WCIS 服务自带各自的落盘 | 「刚才谁来过」查不了 |
| **设备注册表**（device_registry） | 我的 registry 只填了 entity+area，没有 device | klar 的 device 级关联用不上 |
| **用户鉴权 / 权限** | 家庭内网，只做了 `confirm_risky_actions` | 无多用户隔离 |
| **Web 配置面板** | klar 自带 `http://板:10520` UI | 够用 |

## 四、klar engine 到底在做什么（避免误解）

它是**确定性 NLU 解析器**，只做一件事：

```
"打开客厅的灯"  →  {decision:"execute", intent:"HassTurnOn", entity_id:"light.keting"}
```

**它不执行、不认识语音、不合成语音、不存状态。** 所以：

- 只跑 klar = 能听懂你说话，但什么都不发生
- 只跑 executor = 能开关东西，但听不懂人话
- **两者合起来，才等于「HA 的对话代理 + 自动化」那一半**

## 六、一句话总结

**我实现的是「HA 去掉 Web UI 和数据库之后，为了驱动语音控制所必需的那一层」：**
实体表 + 意图执行器 + 状态查询 + 语音 I/O + 多因子安全验证。

**没实现的是 HA 的「长期运行平台」特性**：自动化调度、历史记录、设备注册、多用户。

这些不影响「说一句话就控制板子」的主线，但会影响「它能不能像 HA 一样 7×24 自己跑」。
