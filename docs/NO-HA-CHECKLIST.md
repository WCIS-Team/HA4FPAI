# 不装 HA、全在这块板上：能力对照（2026-10-30 实测）

> 问题：**没有 HA 主机，想把所有东西都放在这块开发板上。**
> 答案：**语音四件套（VAD/ASR/KWS/TTS）已 100% 在板上，不依赖 HA；但「语义理解 + 设备控制」这一层，HA 贡献了 4 样东西，必须由我们自己补。**

## 一、HA 到底提供了什么（4 样，缺一不可）

| # | HA 提供的东西 | 板上有吗 | 不装 HA 的后果 |
|---|---|---|---|
| 1 | **实体表**（房间/设备/命名的唯一真值） | ❌ | klar 回落到内置**德语默认公寓**（`light.wohnzimmer`），播报混德语 |
| 2 | **意图执行器**（把 `HassTurnOn` 真正落到设备上） | ❌ | klar 只「想」不「做」，没有任何东西去按开关 |
| 3 | **设备接入**（Zigbee/WiFi/ESPHome/Modbus 等） | ❌ | 没有设备可控制 |
| 4 | **多轮上下文/状态查询**（实体当前状态从哪来） | ❌ | 「灯开着吗」类问句无数据源 |

**关键认知**：`klar` 不是 HA 的替代品，它是 HA 的**对话代理插件**。它输出 `{intent, slots}`，**执行必须由 HA 完成**。

## 二、板上实测：不装 HA 时的能力边界

我用**手写 registry**（`{version, key, data:{entities:[...]}}`）验证，日志成功加载：

```
7 Entitäten, 5 Räume, 0 Etagen aus Home Assistant geladen
```

**结论**：klar **不要求 HA 运行**，只要求那份 `core.entity_registry` 文件存在。这点是重大利好 —— 我们可以自己造实体表。

### 但随即暴露第二个问题：中文语言包只覆盖固定公寓

`klar lang preview` 显示 zh-CN 包**本身是好的**（不经 registry）：

| 句子 | lang preview 结果 |
|---|---|
| 打开客厅的灯 | **execute** HassTurnOn (0.90) |
| 打开厨房的灯 | **execute** HassTurnOn (0.88) |
| 打开风扇 / 窗帘 | **execute** HassTurnOn (0.88) |
| 客厅灯调到百分之五十 | **execute** HassLightSet (0.90) |
| 打开卧室的灯 | **clarify**（0.83）— 粒度不匹配 |
| 开灯 / 关灯 / 打开所有灯 | **clarify** |
| 打开电视 | clarify（0.00） |
| 把客厅灯调暗 | **reject** |
| 十分钟后提醒我 | **reject** |
| 现在几点 / 你好 | **reject** |

**所以 zh-CN 是"参考实现"级**（官方 README 原话：德语和英语是手写参考包，其它是生成包）。它认得「客厅/厨房」是因为内置公寓恰好有这些房，但**换你自己的房间名/设备名就会退化成 clarify/reject**。

### 我实测踩的坑（供后来者避坑）

registry 必须**两层**结构，缺一层就报错：

```
✅ {"version":1,"minor_version":1,"key":"core.entity_registry",
    "data":{"entities":[...],"deleted_entities":[]}}

❌ {"entities":[...]}            -> missing field `data`
❌ {"data":{"entities":[...]}}   -> missing field `entities`  (版本键必需)
```

## 三、中文常用句子：实测分类清单

### A. klar **现在就能**执行（无需改动）
| 说法 | 意图 |
|---|---|
| 打开/关闭 + **客厅/厨房** + 的灯 | HassTurnOn/Off |
| 打开/关闭 + **风扇/窗帘** | HassTurnOn/Off |
| **客厅灯调到 N%** / 百分之N | HassLightSet |
| 设置一个 N 分钟的定时器 | HassStartTimer |

### B. klar 能识别但**需要澄清**（缺区域/设备粒度）
`开灯` `关灯` `打开所有灯` `关闭所有灯` `打开卧室的灯` `打开电视` `打开空调` `离开模式`
→ 回复「打开什么？」或列出候选房间。**这类只要把实体表做对就能变成 execute。**

### C. klar **完全不会**（需要我们自己补）
| 类别 | 实测失败句 |
|---|---|
| 闲聊/问答 | 你好 · 你是谁 · 谢谢 · 再见 · 现在几点 · 天气怎么样 |
| 指令变体 | 把灯调亮/调暗 · 音量调大/调小 · 静音 · 下一首 · 暂停 |
| 时间表达 | 十分钟后提醒我 · 明天早上七点叫我 |
| 模式/场景 | 睡觉模式 · 回家模式（注：回家模式被误判成 R2D2 回充） |
| 确认答复 | 是的 · 不是 · 取消 · 确认 |
| 组合指令 | 打开灯并且关闭风扇 |

**这不是模型问题，是 zh-CN 语言包的覆盖度问题。**

## 四、不装 HA 的三条路（按投入排序）

### 路线 1：只要语音，不要智能控制（**0 天**，现在就能用）
板上已经有：唤醒 → 识别中文 → 合成播报。
**用途**：语音记事、语音转文字、语音朗读、离线听写。完整的 ASR+TTS 链路。
**缺**：说完「开灯」没人动灯。

### 路线 2：自建"迷你执行层"（**2–3 天**）★ 我推荐
既然 klar 只要一份 registry 文件就能工作，那我们可以自己造设备并执行：

```
mic → KWS(小克) → VAD → ASR → klar engine(10500)
                                    ↓ {intent, slots}
                             ┌──────┴──────┐
                        自建 executor      播报 TTS(10302)
                             ↓
                      GPIO / 继电器 / ESP32 / Modbus
```

**要补的 5 个件**（我可以在板上实现）：
| 件 | 说明 | 工作量 |
|---|---|---|
| 1. `registry` 生成器 | 从你的设备清单生成 `core.entity_registry` | 2 小时 |
| 2. `executor` 服务 | 监听 klar 的 intent，落到具体动作（GPIO/HTTP/MQTT） | 1 天 |
| 3. 中文语言包扩展 | 往 `KLAR_LANG_DIR` 塞自定义句子（补 B/C 类） | 半天 |
| 4. 设备驱动 | 你的灯/风扇是什么接口（继电器？ESP？） | 看硬件 |
| 5. 播报模板 | 把德语默认换成中文（`klar_nlu.json` 覆盖） | 2 小时 |

**注意**：板上 **`/dev/snd` 不存在**，所以 mic 和喇叭也得外接（USB 声卡或走网络）。

### 路线 3：板上装 HA（**不建议**）
已实测不可行：需要 py3.14（板上 3.8.10），且 993 MB 内存不够。详见 `HA-PYTHON-DOWNGRADE.md`。

## 五、直接回答你的三个具体问题

### Q1：不装 HA，sherpa-onnx 会少哪些东西？
**sherpa-onnx 本身一点不少。** 它是纯推理库，VAD/ASR/KWS/TTS 四件全部在板上跑通并通过验收（RTF 0.50/0.54/1.40）。

少的是 **klar engine 的工作前提**：它需要一份实体表，而这张表本来由 HA 维护。

### Q2：播报（TTS）会少什么？
**技术上一点不少，内容上少一句"该念什么"。** 
- matcha 中文 TTS 完全可用（RTF 1.40，8 条样本你已听过）
- 但**播报内容由 klar 生成**，而 klar 的播报模板是德语（`{target} ist an.` / `Lüfter开了。`）
- 不装 HA 也能修：`klar_nlu.json` 覆盖播报模板（2 小时工作量）

### Q3：识别中文，哪些是常用句子？
见上面第三节 A/B/C 三类。**核心结论**：
- 数字类指令（`调到50%`）和明确房间的灯（`打开客厅的灯`）**现在就行**
- 不带房间的（`开灯`）需要实体表做对
- 闲聊和复杂句式**现在不行**，要扩语言包

### Q4：还有什么东西是 HA 有的？
按"不装 HA 就要自己补"排序：

| HA 的能力 | 板上是否已有替代 | 补的成本 |
|---|---|---|
| 实体表 / 房间-设备关系 | 手写 JSON（已验证可行） | 低 |
| 意图执行 | ❌ 完全空缺 | **中（最该补）** |
| 设备接入协议 | ❌ 空缺 | 看你硬件 |
| 状态查询 | ❌ 空缺 | 中 |
| 多轮对话上下文 | klar 自带（conversation_id） | 无 |
| 定时器执行 | ❌ klar 只会"开始定时器"，到期动作没人做 | 中 |
| 自动化/场景 | ❌ 空缺 | 中 |
| Web UI 配置面板 | klar 自带 HTTP UI (10520) | 无 |
| 用户鉴权 | 无（家庭内网可不需） | 低 |

## 六、我的建议（一句话）

**走路线 2。** 你的板子上语音链已经完整可用，真正缺的只是一个 100–200 行的"意图执行器" + 一份你自己的实体表 + 中文播报模板覆盖。**这些我能在这块板上写完，工作量约 2–3 天，不需要 HA。**

需要你先告诉我：**你打算控制什么设备、它们是什么接口**（继电器接线？ESP32？红外？还是先只做语音不控设备）？这决定执行器怎么写。
