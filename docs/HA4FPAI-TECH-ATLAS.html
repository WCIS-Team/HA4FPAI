03 / DESIGN NOTES

关键技术如何协作

切换视图了解语音链、控制语义与裁剪实验。

推理链拆开，资源仍尽量共享。

唤醒词只负责触发后续识别；VAD 切出说话区间，ASR 输出中文文本。语音服务合并为单进程，共用一份 sherpa-onnx / ONNX Runtime，避免多进程重复装载。

  • 入口：麦克风输入在设计链路中从 48 kHz 降到 16 kHz；降采样采用三点平均抗混叠。
  • 理解：klar 只做确定性 NLU 解析，产出 intent 与 slots；它本身不执行命令、不识别语音，也不合成语音。
  • 播报：TTS 产出 22.05 kHz 音频后升采样至 48 kHz；板上缺声卡，因此当前结果写入 WAV。
# 概念链路，不是可直接执行的配置
audio → KWS → VAD → ASR
text → direct phrase | klar NLU
intent + slots → executor → device API → TTS

解析与执行分层，危险动作再设确认门。

master 的执行器提供两条路径：短语表命中时走确定性直连；其余家居表达交给 klar 解析，再统一映射为动作与参数。执行器才是动作落地边界。

  • 通道 B：完整短语匹配，适合少量确定命令，避免把问句或否定句误当执行意图。
  • 通道 A：klar 输出 intent / slots，由 executor 调板端服务；NLU 的安全判定不是系统鉴权。
  • 开门链：仓库记录口令、人脸、防伪 PAD、声纹等多道校验；PAD 未安全标定，因此不能作为开锁依据。
# control 层设计原则（不是 master 当前部署状态）
interpret → proposal → command
idempotency key + explicit confirmation
unknown stays unknown; no silent legacy fallback

裁剪上游，不把裁剪误认为重写。

ha-small 从 Home Assistant Core 上游构建保留集合：从目标功能出发，递归计算 manifest 依赖、静态导入与基础实体域。README 记录上游文件修改数为 0。

  • 保留状态机、事件总线、自动化、脚本、场景、用户认证、Recorder / SQLite、前端与 Assist 语音接口。
  • 隔离 Linux x86_64 实验记录：30/30 功能验证通过；正常进程重启验证 4/4。
  • 功能探针限定在带测试标记的隔离配置目录中；结果不等于板端语音硬件、长期稳定性或生产部署验证。

04 / SYSTEM PRINCIPLES

这套设计的三个取舍

从分支实现提炼，不扩大到尚未验证的能力。

01 — BOUNDARIES

识别、理解、执行分开

模型服务产出文本，NLU 给出结构化提案，executor 决定如何触达设备 API。

02 — RESOURCE

共享重组件，轻量留常驻

板载语音服务合并共享推理运行时；家庭控制主线不依赖完整 HA 容器栈。

03 — EVIDENCE

实验结论带上环境标签

板端实测、隔离容器验证、上游文档事实分别标注，不把一种证据冒充另一种。
